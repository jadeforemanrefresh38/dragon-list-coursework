# Рабочее развёртывание Dragon List

Это эксплуатационная инструкция. Учебный документ из `submission/security-plan` для запуска не требуется и на сервер не передаётся.

## Текущее состояние

Домен: `dragon-list.lol` и `www.dragon-list.lol`. Новое развёртывание: `/opt/dragon-list-java/current` → `/opt/dragon-list-java/releases/2026-10-22-secure`. Старое: `/opt/dragon-list/current`; контейнер старого приложения остановлен и сохранён. Старые пользователи автоматически в новую БД не переносились.

Существующий Caddy `dragon-list-web-1` сохраняет сертификаты и публичные порты 80/443. Маршрут: `dragon-java-waf:8080` → `dragon-java-app:8080` → `db:5432`. Существующая внешняя Docker-сеть — `dragon-list_default`; новые внутренние сети — `172.30.241.0/24` и `172.30.242.0/24`. Перед их созданием проверено отсутствие пересечения с сетями VPN и Docker. БД и Java не подключены к внешней сети; новые порты на хосте не публикуются.

## Файлы и секреты

- `compose.yaml`, Dockerfile, Dockerfile.waf, init-db.sh и waf.Caddyfile находятся в каталоге релиза.
- `app.jar` собирается локально или CI; Node.js и Maven на VPS не нужны.
- `/var/lib/dragon-list-java/production.env` доступен только root (0600). Он содержит RELEASE и три независимых случайных секрета: POSTGRES_ADMIN_PASSWORD, MIGRATOR_PASSWORD, APP_PASSWORD.
- `/var/lib/dragon-list-java/postgres` принадлежит UID/GID 70 и хранит данные PostgreSQL.
- `/var/backups/dragon-list-java` содержит резервные копии с правами 0600, доступные администратору.
- `/var/lib/dragon-list-java/vpn-before.json` — исходный снимок состояния VPN без конфигурационных ключей.
- `/var/lib/dragon-list-java/Caddyfile.before` — сохранённый маршрут к старому приложению.

Сборочный контекст формируется по разрешённому списку: JAR и необходимые файлы `deploy/production`. Dockerfile копирует только `app.jar`; `.dockerignore` исключает остальные файлы из сборки. Не загружайте весь рабочий каталог, `.git`, документы, SSH-ключи или `.env` в образ.

## Проверка и обслуживание

Команды выполняются на собственном VPS с административными правами:

```sh
cd /opt/dragon-list-java/current
docker compose --env-file /var/lib/dragon-list-java/production.env ps -a
docker logs --tail 100 dragon-java-app-1
docker logs --tail 100 dragon-java-waf-1
systemctl status dragon-list-java-backup.timer
systemctl start dragon-list-java-backup.service
python3 test_deployment.py
```

Миграции выполняются одноразовым сервисом `migrate` до запуска приложения. Рабочая роль БД не имеет DDL-прав и доступа к Flyway history. Не используйте её для ручного изменения структуры. После изменения секретов роли БД нужно обновлять согласованно; одна правка env не меняет пароль существующей PostgreSQL-роли.

Образы закреплены по digest. Для обновления подготовьте новый каталог релиза и новый RELEASE, сделайте копию БД, соберите образы, проверьте их отдельно, выполните миграции и тесты. Изменение БД может сделать откат приложения несовместимым; перед миграциями проверяйте обратную совместимость и возможность восстановления. Не запускайте глобальный `docker compose down`, очистку томов или обновление Docker/ОС на VPS с VPN без отдельного плана.

## Резервирование

`backup.sh` установлен как `/usr/local/sbin/dragon-list-java-backup`. systemd-таймер запускается ежедневно в 04:10 по Москве со случайной задержкой до 10 минут. Используются pg_dump custom format, закрытые права, блокировка параллельного запуска и хранение 14 дней. Приложение не может перезаписать каталог копий.

`verify_backup.py` восстанавливает последнюю копию в отдельную БД с именем `dragon_verify_...`, проверяет таблицы и историю миграций, записывает количество восстановленных записей и удаляет только эту временную БД. Он не заменяет рабочую БД. При первоначальной проверке количество записей также сравнивалось с исходной БД; при обычной работе такое сравнение может отличаться из-за новых записей после создания копии. После восстановления рабочей копии отдельно проверяйте содержимое и доступ пользователей, отзывайте старые сессии и убирайте временные тестовые аккаунты. Внешнее резервирование пока не настроено.

## Откат к старому сайту

Сначала проверьте старые данные и возможность входа. Новый и старый сайты имеют разные БД: откат маршрута не переносит новые заметки в старый сайт. Новую БД и её копии сохраняйте.

```sh
docker start dragon-list-app-1
docker inspect -f '{{.State.Health.Status}}' dragon-list-app-1
```

После готовности старого приложения проверьте сохранённый Caddyfile:

```sh
docker exec -i dragon-list-web-1 caddy validate --config - --adapter caddyfile \
  < /var/lib/dragon-list-java/Caddyfile.before
```

Действующий Caddyfile примонтирован как отдельный файл. Его хост-путь — `/opt/dragon-list/releases/2026-10-21-2/deploy/Caddyfile`. Содержимое нужно перезаписать **на месте**, сохраняя inode; атомарная замена через rename оставит контейнер на прежнем файле. После записи выполните:

```sh
docker exec dragon-list-web-1 caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile
systemctl enable --now dragon-list-backup.timer
python3 /opt/dragon-list/current/deploy/vpn_guard.py verify \
  --file /var/lib/dragon-list-java/vpn-before.json
```

Проверьте сайт по HTTPS. Обратное переключение на Java выполняется тем же способом с `edge.Caddyfile` после проверки новых контейнеров. Перед остановкой старого приложения отключите его backup.timer: старый сценарий сам запускает старое приложение после создания копии. Не останавливайте общий внешний Caddy и Amnezia.

## Ограничения хоста

Контейнеры используют общее ядро с привилегированным VPN. Debian 11 вышел из обычной LTS 31.08.2026; совместимость с ОС не означает её защищённость. Root/password-доступ SSH и глобальные правила firewall не изменялись, чтобы сохранить существующий доступ. Безопасное дальнейшее решение — отдельный VPS с поддерживаемой ОС, доступ по ключам и внешние резервные копии. Снимок VPN подтверждает неизменность конфигурационного состояния, но не заменяет проверку туннеля с клиентского устройства.
