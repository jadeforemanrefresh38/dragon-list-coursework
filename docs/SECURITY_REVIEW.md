# Подготовка Dragon List к продакшену

Исторический первичный аудит до развёртывания новой версии. Итоговое состояние и исправленные замечания описаны в [результатах проверки](security/VERIFICATION.md), рабочие настройки — в [инструкции обслуживания](security/DEPLOYMENT.md). Указанные ниже отсутствие лимитов, квот и пагинации относятся к версии до доработок.

Проверка выполнена 22 октября 2026 года через существующий SSH-профиль. На VPS выполнялись только команды чтения состояния. Настройки ОС, Docker, SSH, firewall и Amnezia не изменялись; ключи VPN не читались. Это проверка конфигурации и кода, без сканирования уязвимостей или нагрузочного теста.

## Что работает сейчас

На сервере Debian 11, ядро 5.10 и Docker 20.10.5. Ресурсы: 2 vCPU, около 4 ГБ RAM, на момент проверки доступно около 3 ГБ RAM и 48 ГБ диска. Этого достаточно для планирования ограниченного Java-сервиса, но допустимая нагрузка пока не измерена.

Публичные TCP-порты 80 и 443 уже заняты Caddy старого Dragon List. Старый сервер приложения работает в отдельном контейнере без опубликованного порта 8000, от UID 10001, с read-only корнем, no-new-privileges, лимитом 768 МБ RAM и 1 CPU. Java-версия в этот момент работает только локально.

Amnezia AWG2 находится в отдельном контейнере и использует UDP. Контейнер имеет privileged=true и возможности NET_ADMIN/SYS_MODULE. Это описание существующей установки, а не рекомендация расширять права других контейнеров. После проверки время запуска Amnezia осталось прежним, счётчик перезапусков — 0. Реальный обмен VPN-трафиком в этой проверке не измерялся.

## Рекомендуемое размещение

Предпочтительный вариант — отдельный VPS с поддерживаемой Debian для Java-приложения. Amnezia остаётся на текущем сервере. Это уменьшает общий ущерб от компрометации сайта и не связывает доступность VPN с нагрузкой на сайт. Рекомендация основана на разделении хостов и наблюдаемой привилегированности VPN-контейнера.

Если остаёмся на одном VPS:

1. Использовать существующий Caddy для HTTPS и отдельного домена/поддомена. Шаблон nginx из deploy/ нельзя просто включить на 80/443 этого сервера: порты уже заняты.
2. Java-приложение запускать отдельным непривилегированным пользователем или контейнером с read-only файловой системой, no-new-privileges и минимальными capabilities. Не подключать docker.sock, каталоги VPN, SSH-ключи и резервные копии.
3. PostgreSQL оставить во внутренней сети без публичного 5432. Для нового проекта использовать отдельные БД, учётную запись и данные. Приложение не должно иметь доступа к старой БД. Для продакшена разделить роль миграций и рабочую роль с правами только на необходимые таблицы/последовательности.
4. В сетевом варианте Docker Caddy обращается к приложению по имени контейнера в согласованной сети. localhost внутри контейнера Caddy не является localhost хоста. Сеть БД и её адресацию выбрать после проверки пересечений с существующими сетями.
5. Начать с Xmx512m, лимита около 1 ГБ RAM для Java-процесса и около 1 CPU; настроить лимиты БД, логов и диска, затем проверить нагрузку. Это стартовые параметры для измерения, а не гарантия производительности.
6. До любых сетевых изменений сохранить текущие правила, состояние Amnezia и доступ к консоли провайдера; после проверить реальный VPN-трафик с клиентского устройства. Перезапуски Docker и изменения правил VPN не входят в обновление сайта.

Контейнеры используют ядро хоста. Сети и ограничения прав уменьшают поверхность атаки, но не дают такую же границу изоляции, как отдельная виртуальная машина. При публикации контейнерных портов Docker создаёт свои правила: одного настройки UFW недостаточно без проверки фактического маршрута пакетов.

## Защита в Java-приложении

Уже реализованы BCrypt, CSRF, серверные сессии с HttpOnly/SameSite и Secure в prod, проверка владельца каждой записи и изображения, параметризованные SQL-запросы, проверки полей, безопасный вывод Markdown, ограничения изображения 5 МБ / 4096 × 4096 и перекодирование файлов. Массовые операции проверяют все идентификаторы до изменения данных и выполняются в транзакции.

До продакшена нужны: ограничение частоты входа и регистрации, квоты и пагинация, CSP/Permissions-Policy под текущий интерфейс, журнал событий без паролей и текста заметок, внешние резервные копии с проверкой восстановления, проверка зависимостей, тесты на целевой PostgreSQL и нагрузочная проверка. CSP сначала проверять в режиме Report-Only: клиент использует inline-стили для тегов и прогресса, поэтому произвольная строгая политика может сломать интерфейс.

В проекте 8 JUnit-тестов в двух классах: 3 проверки базовых форм и 5 проверок расширенного API. Это интеграционные тестовые методы с несколькими проверками внутри, а не отдельные unit-тесты каждого метода. Браузерные проверки запускались отдельно и в число 8 не входят. CI собирает клиент и выполняет Maven verify на Java 17. Текущий набор использует H2; PostgreSQL и конфигурация реального сервера требуют отдельного этапа проверки.
